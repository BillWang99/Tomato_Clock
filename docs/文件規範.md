# 文件規範

目的：文件只能有一個真相，後續擴充有固定的放法，避免越寫越多、彼此矛盾。
本檔本身是規則，改它要說明理由。

## 1. 四層結構：每份文件只屬於一層

| 層 | 目錄 | 回答的問題 | 改動時機 |
|---|---|---|---|
| 規則 | `CLAUDE.md` | 開發時**必須遵守什麼** | 很少改；只放規則與「去哪裡查」，上限 150 行 |
| 規格 | `docs/規格/` | 系統**現在長什麼樣** | 功能上線的**同一個 commit** 一起改 |
| 計劃 | `docs/計劃/` | 我們**打算怎麼改** | 設計期間；上線後把定案內容併入規格，原檔搬 archive |
| 紀錄 | `docs/紀錄/` | **何時做了什麼、為什麼** | 只新增、不修改 |

另外兩個目錄不屬於四層：`docs/外部文件/` 放原廠規格書，只放不改；`docs/archive/` 放被取代的文件，只進不出。

**衝突時的優先序**：程式 > 規格 > 計劃 > 紀錄。發現規格與程式不符，改規格，不改程式去遷就文件。

## 2. 規格層：一個領域一份，不可重複

新功能歸入既有領域，**不新開檔**；真的要新開領域，先在 README 登記。

每份規格的固定開頭：

```
# 訂單與出貨
最後核對：2026-01-01（對應版本 abc1234）
程式範圍：app/Modules/Order
相關規則：CLAUDE.md §3
```

規格寫「現在是什麼」，不寫「以前是什麼」「打算變成什麼」。

### 功能清單（bstack 會檢查）

每份規格都有一節「功能清單」，每個功能一列：

| 功能 | 入口 | 風險 | 驗收案例 | 測試檔 |
|---|---|---|---|---|
| 建立訂單 | POST /orders | 高 | 3 件商品各 100 元 → 總額 300 | tests/Feature/OrderCreateTest.php |

- **入口**：路由、API、MCP 工具名稱。bstack 會比對路由清單，沒登記的入口會被擋。
- **風險**：高（金額、權限、資料變更）／中（表單、審核流程）／低（CRUD、畫面）。
- **驗收案例**：輸入什麼 → 應該得到什麼。高風險必填。
- **測試檔**：高風險必填；雛形階段中低風險可先空著。

### 細節資料夾 `規格/<領域>/`

入口文件放不下的長篇設計放在與入口同名的資料夾。入口文件是唯一的「現況」，衝突時以入口為準。

## 3. 計劃層：有生命週期

每份計劃第一行必須有狀態：`狀態：草案｜討論中｜已定案｜已實作｜放棄`。

- **已實作**：把定案內容併入對應規格（同一個 commit），檔案搬到 `docs/archive/`。
- 放棄：搬 archive，開頭寫一行放棄原因。

`docs/計劃/` 裡任何時候不該超過十份。

## 4. 紀錄層：只追加

- `上線紀錄.md`：每次發版一段，日期倒序。內容：版本、改了什麼、跑了哪些 migration、備份位置、上線後驗證結果。
- `決策紀錄.md`：一件事一段，格式「日期／決定／理由／影響哪份規格」。
- 會議紀錄一次一檔，檔名 `會議_YYYY-MM-DD_主題.md`。

紀錄不修改。寫錯了，新增一段更正。

## 5. 命名與索引

- 檔名用中文主題，不帶日期（紀錄層除外），不帶版本號。
- **新增任何文件的同一個 commit 必須更新 `docs/README.md`**。
- 程式註解引用文件時只寫規格層的檔名。
- 日期一律 `YYYY-MM-DD`。

## 6. 什麼時候要動文件

| 情況 | 要做的事 |
|---|---|
| 新功能開發前 | 在 `docs/計劃/` 開一份草案 |
| 功能上線的 commit | 併入規格、計劃搬 archive、上線紀錄加一段、README 更新 |
| 改了遠端設定 | 上線紀錄加一段 |
| 做了取捨決定 | 決策紀錄加一段 |
| 修 bug、文案 | 只寫上線紀錄 |
